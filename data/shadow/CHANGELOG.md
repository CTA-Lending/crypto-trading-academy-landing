## CHANGELOG-001 · 🔴 資金費被乘以 3(**重大**,影響主指標)

| | |
|---|---|
| 生效日 | **2026-08-04**(下一個決策日) |
| 發現日 | 2026-08-03 |
| §9 分類 | 允許類別:「修補會造成錯誤估值的 bug」 |
| 影響期間 | **2026-07-22 ~ 2026-08-03(第 1~12 決策日)全部受影響** |

**根因**:`shadow/multi.py::funding_cost()` 內為 `total += u * p * r * 3`。
那個 `× 3`(一天 3 期 × 8 小時)在 `r` 是**單一即期費率**時是正確的;
但 v3 之後傳入的 `r` 來自 `universe.accumulate_funding()`,
**它回傳的已經是「窗口內所有結算的加總」** → 重複換算,**超收/超付 3 倍**。

`fetch_funding_since()` 的 API 失敗退路回傳 `float(r) * 3`(該處 `r` 確為即期費率,
所以那個 ×3 是對的),經過 `funding_cost` 後變成 **×9**。

**量級**(公開端點 `fapi/v1/fundingRate` 實查,2026-07-24 UTC 全日):
```
DEXEUSDT   24 筆結算 / 間隔 1h / 當日加總  -7.618%
```
單一標的單日資金費即達 -7.6%,乘 3 後 -22.9%。**這是百分點級,不是捨入誤差。**

**對主指標的影響**:預先登記的主指標是「相對 `bench_eqw` 的 Information Ratio」,
而 `bench_eqw` 100% 做多的正是資金費深度為負的標的(空方付多方)→ 超收在多頭身上
變成**超付的紅包**。因此**基準本身被高估**,所有相對它的 IR 被系統性壓低。

**修法**:移除 `funding_cost` 內的 `× 3`。日/期換算的責任歸於取數層。

> ⚠️ **修正後的重述數列尚未由本團隊獨立重跑驗證,因此本文件不列出任何重述後的數字。**
> 重跑完成後將以 **CHANGELOG-006** 追加,並依 §9 分段呈現。
> 在此之前,**第 1~12 決策日的損益數字不得用於任何對外績效陳述**。

## CHANGELOG-002 · 🔴 資金費抓取分頁不足導致時間軸錯位(**重大**)

| | |
|---|---|
| 生效日 | **2026-08-04** |
| §9 分類 | 允許類別:「修補會造成錯誤估值的 bug」 |
| 影響期間 | 2026-07-22 ~ 2026-08-03,**僅影響結算間隔 < 8 小時的標的** |

**根因**:`shadow/universe.py::fetch_funding_since()` 使用 `limit=20` 單次抓取。
但幣安的 `fundingIntervalHours` 並非每檔都是 8 小時 —— 公開端點 `fapi/v1/fundingInfo` 實查:

| 標的 | 間隔 | 每日結算筆數 |
|---|---|---|
| DEXEUSDT / COTIUSDT / BANKUSDT | **1 小時** | **24** |
| RIFUSDT / ESPORTSUSDT / AKEUSDT / EULUSDT | 4 小時 | 6 |
| WLDUSDT / ETHUSDT 等 | 8 小時 | 3 |

一天 24 筆卻只抓 20 筆 → cursor 每天落後 4 小時,而且**逐日累積**。
後果不是「少算」,而是**兩天前的極端費率被套用在今天已經改變的部位規模上** ——
時間軸本身錯位,**無法用固定係數校正**。

**修法**:改為分頁抓取(`limit=1000`,迴圈至追上或無新資料,50 頁上限防呆),
`accumulate_funding()` 的 exactly-once cursor 語意不變。

## CHANGELOG-003 · 公開的兩個 JSON 對同一格給出互斥數值

| | |
|---|---|
| 生效日 | **2026-08-03**(本次發布即生效) |
| §9 分類 | 允許類別:修補錯誤估值 |

**發生什麼**:同一次推送(commit `26615ed`, 2026-08-03 08:36Z)同時發布:
- `dashboard_data.json` → 2026-07-25 規則腦 **-28.18%**、等權多頭 **+29.68%**(正確)
- `diaries.json` → 同日同腦 **-0.395%** / **+0.09%**(錯誤)

**根因**:CHANGELOG-000 的修補只改了寫入端,`journal[].outcome` 的**歷史值未回填**,
而 `diaries.py` 讀的正是它。今日發布的 10 日滾動視窗 × 9 競爭者 = 90 格中,
**16 格(17.8%)仍為錯值**。

`diaries.json` 未被任何 HTML 連結,因此團隊內部無從察覺其損壞。

**修法**:`diaries.py` 改為與儀表板共用同一個權威來源
(`daily_returns.daily_return_table`,即 PROTOCOL §6 鎖定的 `equity_t/equity_{t-1}−1`)。
**刻意不回填 `journal`** —— 那是已被外部錨定的原始紀錄,不應追溯改寫。

**驗證**:修補後逐格比對兩檔,分母 90 格 → **不一致 0 格**。

## CHANGELOG-004 · `temperature = 0.0` 從未被實際送出(**紀錄更正**)

| | |
|---|---|
| 生效日 | **2026-08-03**(僅更正紀錄,**不改變受試者行為**) |
| §9 分類 | 紀錄更正 |

**發生什麼**:`forward_multi.py` 的 `LLM_PARAMS` 記錄 `"temperature": 0.0`,
且該 dict 每日寫入帳本並納入外部錨定。但實際發出請求的
`sliceb/llm_router.py::call_llm()` **函式簽名中沒有 temperature 參數**,
request body 亦未攜帶 → 第 1~12 決策日全部運行於各供應商的預設行為。
**⚠️ 確切數值未由本系統記錄,因此不得宣稱「實際為 1.0」** —— 可確認的只有「未送出」。

**後果**:一個宣稱不可竄改、每日錨定的參數,記錄的是一件從未發生的事。
**本 Run 的 LLM 決策不可重現。**

**修法選擇說明**:**刻意不改為「真的送出 temperature=0」**。
那會在實驗進行中改變受試者行為,違反 §9「禁止修改受試者」。
正確處理是把紀錄改為真實描述,行為維持原樣。
決定性(temperature=0)留待 **Run #2** 預先登記。

## CHANGELOG-006 · 曝險檢查的適用範圍未揭露(**陳述更正**)

| | |
|---|---|
| 生效日 | **2026-08-04**(僅更正陳述,**不改變任何受試者行為**) |
| §9 分類 | 陳述更正 |

**發生什麼**:總曝險上限(100%)的檢查位於 `multi._parse_alloc()` 內,
而該函式**只被 `llm_allocation()` 呼叫**。因此:

| 受試者 | 是否經過曝險檢查 |
|---|---|
| gpt / gemini / claude / gpt_pure / guardian(5 個 LLM 腦) | ✅ 是 |
| **rule(規則腦)** | ❌ **否** |
| bench_btc / bench_eqw / bench_cash(3 個市場基準) | ❌ 否 |

`rule_allocation()` 與 `benchmark_allocation()` 直接回傳權重,不經過解析與檢查。
公開資料檔 `dashboard_data.json` 的 `violations` 中 rule = 0,
**代表「未受檢查」,不代表「未逾越」**。

實測:規則腦於 **2026-07-25** 的 mark-to-market 實際總曝險達 **174.6%**,
當日無任何違規紀錄或告警。

**修法選擇說明**:依 §9「**禁止**修改風險上限」,不得於 Run #1 進行中對 rule 新增約束
—— 那會改變受試者行為。因此只做兩件事:
1. 資料檔新增 `violation_checked` 欄位,明確標示每個受試者是否受檢查
2. 公開頁「紀律紀錄」區塊加註適用範圍與 174.6% 的實測值

即:**改的是裁判的記分板,不是受試者的行為。**

**誠實補充**:公開頁的違規表格原本就只列出 5 個 LLM 腦,rule 與基準並未出現在該表,
因此該表本身未曾對 rule 作出「0 違規」的陳述。真正缺乏揭露的是
「這個量測只適用於一部分受試者」這件事,以及公開資料檔中的 `violations` 欄位。
