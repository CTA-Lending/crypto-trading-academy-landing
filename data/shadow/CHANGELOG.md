## CHANGELOG-001 · 🔴 資金費被乘以 3(**重大**,影響主指標)

| | |
|---|---|
| 生效日 | **2026-08-04**(下一個決策日) |
| 發現日 | 2026-08-03 |
| §9 分類 | 允許類別:「修補會造成錯誤估值的 bug」 |
| 影響期間 | **2026-07-22 ~ 2026-08-03(第 1~12 決策日)全部受影響** |

**根因**:`shadow/multi.py::funding_cost()` 內為 `total += u * p * r * 3`。
那個 `× 3`(一天 3 期 × 8 小時)在 `r` 是**單一即期費率**時是正確的;
但 v3 之後傳入的 `r` 來自 `universe.accumulate_funding()`,
**它回傳的已經是「窗口內所有結算的加總」** → 重複換算,**超收/超付 3 倍**。

`fetch_funding_since()` 的 API 失敗退路回傳 `float(r) * 3`(該處 `r` 確為即期費率,
所以那個 ×3 是對的),經過 `funding_cost` 後變成 **×9**。

**量級**(公開端點 `fapi/v1/fundingRate` 實查,2026-07-24 UTC 全日):
```
DEXEUSDT   24 筆結算 / 間隔 1h / 當日加總  -7.618%
```
單一標的單日資金費即達 -7.6%,乘 3 後 -22.9%。**這是百分點級,不是捨入誤差。**

**對主指標的影響**:預先登記的主指標是「相對 `bench_eqw` 的 Information Ratio」,
而 `bench_eqw` 100% 做多的正是資金費深度為負的標的(空方付多方)→ 超收在多頭身上
變成**超付的紅包**。因此**基準本身被高估**,所有相對它的 IR 被系統性壓低。

**修法**:移除 `funding_cost` 內的 `× 3`。日/期換算的責任歸於取數層。

> ⚠️ **修正後的重述數列尚未由本團隊獨立重跑驗證,因此本文件不列出任何重述後的數字。**
> 重跑完成後將以 **CHANGELOG-006** 追加,並依 §9 分段呈現。
> 在此之前,**第 1~12 決策日的損益數字不得用於任何對外績效陳述**。

## CHANGELOG-002 · 🔴 資金費抓取分頁不足導致時間軸錯位(**重大**)

| | |
|---|---|
| 生效日 | **2026-08-04** |
| §9 分類 | 允許類別:「修補會造成錯誤估值的 bug」 |
| 影響期間 | 2026-07-22 ~ 2026-08-03,**僅影響結算間隔 < 8 小時的標的** |

**根因**:`shadow/universe.py::fetch_funding_since()` 使用 `limit=20` 單次抓取。
但幣安的 `fundingIntervalHours` 並非每檔都是 8 小時 —— 公開端點 `fapi/v1/fundingInfo` 實查:

| 標的 | 間隔 | 每日結算筆數 |
|---|---|---|
| DEXEUSDT / COTIUSDT / BANKUSDT | **1 小時** | **24** |
| RIFUSDT / ESPORTSUSDT / AKEUSDT / EULUSDT | 4 小時 | 6 |
| WLDUSDT / ETHUSDT 等 | 8 小時 | 3 |

一天 24 筆卻只抓 20 筆 → cursor 每天落後 4 小時,而且**逐日累積**。
後果不是「少算」,而是**兩天前的極端費率被套用在今天已經改變的部位規模上** ——
時間軸本身錯位,**無法用固定係數校正**。

**修法**:改為分頁抓取(`limit=1000`,迴圈至追上或無新資料,50 頁上限防呆),
`accumulate_funding()` 的 exactly-once cursor 語意不變。

## CHANGELOG-007 · 🔴 資金費取數層的兩個靜默失效路徑(**未曾觸發,預防性修補**)

| | |
|---|---|
| 實際生效日 | **2026-08-21** |
| 揭露日 | 2026-08-21(同日) |
| §9 分類 | 允許類別:「修補會造成錯誤估值的 bug」 |
| 是否影響既有樣本 | **否** —— 兩條路徑在 Run #1 全部 30 個決策日中**一次都沒有觸發**(`data/multi_daily.log` 中「資金費近似」出現 0 次),故不切分樣本、不作廢任何日期 |

**起因**:CEO 於 2026-08-21 要求「幣圈爆漲,查影子實驗室結算報價是否正常」。
報價本身查無異常(逐檔對幣安即時價,18 檔最大偏差 2.9%,無凍結價;
資金費符號與量級以原始結算歷史獨立重算,−7.08 vs 帳上 −7.40,差異由
「系統用重配置前的舊倉、複算用重配置後的新倉」完全解釋)。
異常出在**翻閱取數層時發現的兩條從未走過的路**。

**洞一 · 靜默丟棄**:`universe.fetch_funding_since()` 的 except 分支中,
歷史與當期兩條路都失敗時是 `continue` —— 該幣直接從回傳 dict 消失。
呼叫端 `rates.get(b)` 取得 `None`,`multi.funding_cost()` 跳過它,
**該幣當日資金費為 0**。而警示清單以 `fr.get(sym, {}).get("approx")` 計算,
對不存在的 key 回 `None`,因此**它連警示清單都進不去**。
實測後果:18 檔中漏 1 檔 DOGE(名目 40,500)= 少收 36.45 USDT,無任何紀錄。

**洞二 · 退路重複計費**:退路回傳 `即期費率 × 3` 供呼叫端扣款,同時
(正確地)不推進 cursor 以便回補。但隔日恢復時,`accumulate_funding` 從舊
cursor 起算,**把同一批結算再收一次**。實測:每日 3 期 × 0.01%,壞一天再恢復
→ 兩日合計收 0.0009,真實應為 0.0006,**多收 50%**。

**洞三 · 守衛單向**:`invariants.FUNDING_MAGNITUDE` 只擋「金額 > 淨值 15%」。
金額 0 永遠通得過。一道只覆蓋單一方向的判準,擋不住相反方向的失效。

**修補**:
1. 取數層改為**契約保證每檔都回**;失敗時回一筆標記過的零
   (`approx=True`、`failed=True`、附 `spot_hint` 診斷值、cursor 不前進)。
2. 退路**一律不計費**(`total=0`)。cursor 未前進,金額由下一次成功的窗口
   完整補齊 —— 寧可「日期錯一天」也不要「金額錯一倍」:前者可稽核,後者會複利。
3. 新增純函式 `multi.funding_coverage()`,以**獨立於金額的來源**量測涵蓋率,
   分開回報 approx / failed / missing 三種不同的失效,寫入每日紀錄與 run_meta。
4. 不變式補三條雙向守衛:`FUNDING_COVERAGE`(漏檔)、`FUNDING_UNREACHABLE`
   (問不到)、`FUNDING_INCOMPLETE`(不完整比例 > 20% 為 critical,否則 warn)。

**驗證**:新增 `tests/test_funding_coverage.py` 17 條。
六道守衛逐一以突變測試反向對照 —— **每一道拿掉,測試都會紅**
(3 / 2 / 2 / 1 / 1 條失敗)。全案測試 3,403 → 3,420 條,全過。

**為什麼記在這裡**:這兩條路徑從未觸發,依 §9 嚴格說可不記錄。但
CHANGELOG-001 與 -002 都是資金費的錯,且都在**已經影響 12 個決策日之後**
才被發現。「問不到」與「沒有資金費」在損益上長得一模一樣,是本專案
第八次踩到的同一個盲點 —— 這種盲點值得在它咬人之前就留下紀錄。

## CHANGELOG-008 · 🔴 基建故障會被記錄成流動性事件並砍 20%(**未曾觸發,預防性修補**)

| | |

| 實際生效日 | **2026-08-21** |
| 揭露日 | 2026-08-21(同日) |
| §9 分類 | 允許類別:「修補會造成錯誤估值的 bug」 |

報價取數層(`fetch_execution_prices`)有沒有同一個毛病?有,但方向相反 —— 而
方向相反的那一種更貴。

**問題**:`fetch_execution_prices()` 整包 `fetch_tickers` 失敗、逐檔重試又全失敗時,
回傳空 dict。下游 `run_day()` 的判斷是 `missing = [x for x in units if x not in px]`
—— 於是**每個腦的每一檔持倉同時變成「無報價」**。接著:

- 連續 `STALE_MAX_DAYS = 3` 日 → **全體強制平倉**,套用 `STALE_EXIT_HAIRCUT = 20%` 折價

## CHANGELOG-015 · ⚠️ 錨點 seq 48 的公開檔案雜湊對不上下載到的檔案(換行,非竄改)

| | |
|---|---|
| 影響 | 錨點鏈 **seq 48**(2026-09-06T00:36:56Z)的 `published` 欄位 |
| 揭露日 | 2026-09-06(**當日**) |
| 對數據的影響 | **無**。三個檔案一個位元組都沒有被人動過 |

**現象**:任何人在 2026-09-06 下載公開檔案並執行 `verify_chain.py`,
會看到三個檔案被判「✗ 不符」:

```
   ✓ CHANGELOG.md           鏈上 f44bdad95d0b2b21  現在 f44bdad95d0b2b21
   ✗ PROTOCOL.md            鏈上 1b953e4d9e218ef0  現在 603a62467f936a39

```

🔴🔴 **這是最糟的一種失敗:我們自己的驗證器在指控我們竄改數字。**

**根因**:雜湊取自**本機工作區的位元組**,而全世界下載到的是
**git 正規化之後的位元組**。Windows 上文字模式寫檔產生 CRLF,
`core.autocrlf=true` 讓 git 在 commit 時轉回 LF,GitHub Pages 送出 LF 版
→ 兩者永遠對不上。CHANGELOG.md 之所以相符,只是因為它本來就是 LF。

**可自行複現**:把下載到的檔案 `LF → CRLF` 之後取 sha256,會等於鏈上記的值。

⭐ **假警報也是傷害**,而一個會誣指自己的驗證器**比沒有驗證器更糟** ——
它會訓練所有人忽略紅燈。

### 修法(三層,全部已上線)
1. `anchor.py` 新增 `normalize_published_eol()`,在**取雜湊之前**把公開檔案
   統一成 LF。🔴 刻意**不是**「改成算正規化後內容的雜湊」——
   那樣雜湊描述的就不是任何真實存在的檔案了;而是**讓檔案本身就是 LF**,
   於是「工作區 = git blob = 網站送的」三者是同一串位元組。
2. `landing-page/.gitattributes` 加上 `data/shadow/** -text`,
   讓 git 不再對這些檔案做任何換行轉換。
3. `verify_chain.py` 會**分辨「只差換行」與「內容被改」**並印出診斷。
   🔴 但這**不是免死金牌**:仍然判為不符,只是多說一句它是哪一種。
   有反向對照測試守著:數字真的被換掉時,不准被說成「只差換行」。

### 🔴 seq 48 這一筆不會被修正
錨定鏈是 append-only。seq 48 記的雜湊就是當時算出來的值,錯了也留著。
**從 seq 49 起**(2026-09-07 的排程)雜湊會與下載到的檔案一致。
在那之前,驗證器對這三個檔案會顯示「✗ 不符(內容相同,只差換行)」。

### 為什麼沒有補跑一次錨定把它變綠
補跑會在同一個決策日多產生一筆錨點,只為了讓畫面好看。

```
    continue            # ← 帳本沒有 returns 可比 = 通過
```
而這個函式的 docstring 自己寫著
「**這個函式存在的目的就是讓這種錯不會再無聲發生**」。
對帳的分母只有「剛好帶了 returns 欄位的那些格子」,而且**從不回報涵蓋率** ——
哪天整批 returns 掉了,頁面會顯示一個漂亮的「0 筆不一致」。

→ 分成 `mismatch`(真的不一致)/ `missing_returns`(帳本沒得比)/
`underivable`(帳本有值但我們算不出來)三種,**沒比到的不算通過**。
公開頁現在印「對帳涵蓋率:**已比對 X/Y 格**」,沒比到的另外點名。

📌 **今日實測 549/549 格全部算得出來**,所以這兩條是**潛伏**缺陷,
不是正在發生的錯報 —— 而這句話由程式每天重算,不是我們記得。
「不一致 22 筆、修正日之後 0 筆」的數字**沒有任何改變**。

### 順帶抓到的兩個(都是修上面那兩條時撞出來的)

## CHANGELOG-042 · 一盞設計上不可能亮的燈

| | |
|---|---|

### M042 🔴🔴 「當日未能結算 0 / 61 個決策日」—— 那個 0 是**量不到**,不是沒發生
這一頁的事件表有一列「當日未能結算」,61 天全是 0。
而 `unsettled` 這個欄位**全程沒有任何寫入端** ——
程式裡沒有一行會把某一天標成「未能結算」,所以它結構上永遠是 0。

兩份模組契約卻寫著:
> 任一持倉幣無法估值 → 該腦當日標記 UNSETTLED,**不計入正式績效**

**這道防線不存在。** 缺價時真正走的是另一條路:
以**最後已知價**估值並標記 `stale`,連續無報價才折價強制出場 ——
那一天的估算值**照樣進入公開的 equity_curve 與 metrics**。
而每日日誌還天天印「UNSETTLED 0」,讓人以為防線在運作、只是沒觸發。

⭐⭐ **一盞設計上不可能亮的燈,比沒有那盞燈更糟。**
沒有那一列,讀者知道自己不知道;有那一列,讀者以為自己檢查過了。

→ 兩份契約改成描述**現況**(原句標示為已更正);
事件表那一列改印「**機制未啟用**」,並寫明
「這一格不是『沒發生過』,是**量不到**」。

**🔴 要不要真的把那道防線做出來,會改動已經公開的績效數字 —— 留給 CEO 拍板。**
在那之前,頁面說的是實話:它沒有啟用。

守衛**兩個方向都驗**:現在沒有寫入端 → 旗標必須是 False;
哪天真的有人實作了,測試會**轉紅**,逼旗標改成 True、那一列自動變回正常顯示。
(沒有後面這半,這份守衛自己就是下一個「永遠綠」的關卡。)

### M019 卡片的樣本數用了**全體**天數,而報酬率的分母是**逐腦**天數
卡片上的報酬率來自 `metrics[b]`(分母 = 該腦自己的天數),
底下那行小字卻印 `meta.epoch2_days`(全體共用)。
未結算日與缺格淨值都不計入該腦的 metrics —— 一旦分岔,
讀者會拿一個比真實樣本**大**的分母去理解那個報酬率。

→ 改讀逐腦天數;分岔時卡片自己標「⚠️ 此腦有 N 日未計入,上方報酬率的分母是 N 日」;
拿不到就明講「天數未提供」,不退回全體值再印一個假分母。

📌 今日實測 9/9 都是 49 日,**沒有分岔** —— 這是潛伏的錯,不是正在發生的;
而這句話由程式每天重算,不是我們記得。

### 順帶:一條守衛掃到了自己要防的東西
`test_事件揭露要帶分母_而且逐日算` 會掃事件區塊裡有沒有**寫死的日期**,
而它掃的是整段原始碼 —— 於是一則說明**註解**裡的日期就把它弄紅了。
⭐ 它自己上面三則註解都在講「掃字串量到的是鍵名,不是行為」,
而它本身犯了同一個病。改成先剝註解再掃,並以突變確認它仍抓得到真正寫死的日期。

真的加上 `unsettled` 寫入端而旗標沒跟上 → 轉紅)。
